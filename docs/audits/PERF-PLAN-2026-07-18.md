# teru + teruwm — performance improvement plan (2026-07-18)

Grounded in reading the actual render/event-loop code, not just the audit one-liners.
Ordered by (benefit ÷ risk). Every item lists root cause, fix, risk, and how to verify —
because the project rule is *never ship a render change you haven't reproduced on hardware*.

## Context: where the two binaries actually stand

- **teruwm `TerminalPane.renderIfDirty`** (`src/compositor/TerminalPane.zig:416`) is already
  good: it renders **only dirty rows** on the CPU (`renderDirtyWithSelection`) and honors a
  `max_render_fps` throttle that keeps the grid dirty and reschedules instead of painting
  faster than the cap. The *only* remaining waste is that it presents **full-buffer GPU
  damage** (`dirty_y0 = -1`) unless `wm_config.partial_damage` is set — because the nvidia
  GLES path truncated glyphs under partial damage (the June scrollback-FPS incident). So on
  teruwm, CPU is cheap; the cost is GPU re-upload of the whole pane per paint.
- **teru windowed `Multiplexer.renderAllWithSelection`** (`src/core/Multiplexer.zig:584`) is
  the opposite: it `memsetU32`s the **entire** framebuffer and repaints **every cell of every
  pane** on any dirty frame. Dirty-row tracking exists (`grid.dirty_row_min/max`,
  `markRowDirty`) and is faithfully maintained — but the CPU renderer never consults it. The
  cursor-blink "mark only the cursor row" comment at `windowed.zig:1498` is therefore a no-op:
  flipping the caret repaints the whole screen.

## Tier 1 — highest leverage, ties directly to the power-drain incidents

### 1.1 Enforce the frame cap on the *render*, not just the idle sleep (teru windowed)
- **Where:** `src/modes/windowed.zig:1529` (the `if (any_dirty and !sync_active)` render block)
  vs. the cap computed at `:1655` (`frame_min_ns = 16.67 ms`).
- **Root cause:** the 60 fps cap only shortens the `poll()` timeout. When a PTY fd is readable
  (data flooding in), `poll` returns immediately, the loop reads a bounded chunk, sets dirty,
  and renders a **full screen** — with no check that 16 ms elapsed since the last paint. Result:
  one full-screen repaint per read chunk (~8 KB) under load (`cat bigfile`, fast scrolling).
- **Fix:** gate the render on `now - last_render_ns >= frame_min_ns`; if too soon, leave
  `grid.dirty` set and let the already-scheduled frame-cap wake coalesce the batch. This is
  exactly the pattern teruwm's `TerminalPane` already uses (`:469`). ~15 lines.
- **Benefit:** collapses N full repaints per frame into 1 under heavy output — the dominant
  CPU cost during scrollback/build output. **Risk:** low-medium (timing only, output unchanged).
  **Verify:** `time seq 1 200000` in windowed teru, compare CPU%; check no visible lag on typing.

### 1.2 Make `renderAllWithSelection` honor dirty rows (teru windowed)
- **Where:** `src/core/Multiplexer.zig:594` (full memset) + the per-pane render loop.
- **Root cause:** full-framebuffer clear + full per-pane repaint every frame, ignoring
  `dirty_row_min/max`. On a 2560×1600 buffer that's ~16 MB of write bandwidth to flip one caret.
- **Fix (staged):** (a) skip the global `memsetU32` — only clear the gap/pad regions that
  aren't overwritten by a pane; (b) pass each pane's dirty-row range into the pane renderer so
  only changed rows are re-blitted; (c) emit a partial-damage rect to the platform layer
  (X11 SHM `xcb_shm_put_image` sub-rect / Wayland `surface.damage`) instead of full-surface.
  Mirror teruwm's `partial_damage` structure so both share one code path.
- **Benefit:** the big idle/interactive win for standalone teru — matches the 0.45%→13% gap
  measured on teruwm. **Risk:** medium-high (this is where partial damage bit us before on GLES;
  the SHM path is simpler but still needs pixel verification). **Verify:** screenshot-diff
  before/after on typing, scrolling, split layouts, selection, wide glyphs; watch for stale rows.

### 1.3 Land `partial_damage` as the default on teruwm
- **Where:** `src/compositor/TerminalPane.zig:502` (`dirty_y0 = -1` unless `partial_damage`).
- **Root cause:** partial GPU damage is implemented but default-off because nvidia GLES
  truncated glyph bottoms (rows damaged at cell-top, glyph descenders below the rect stale).
- **Fix:** expand each dirty-row damage rect by the glyph descent / a one-cell bleed, or damage
  `[row_min-0 .. row_max+1]` in *pixels including descent*, then flip the default on. Alternatively
  switch the readback to the pixman software path where the truncation doesn't occur.
- **Benefit:** eliminates full-pane GPU re-upload per paint — the remaining teruwm idle-power
  cost. **Risk:** medium — GLES-specific, MUST be verified on the user's nvidia hardware.
  **Verify:** the user runs teruwm on the 4070, streams output + scrolls, confirms no glyph
  truncation; measure package power idle vs. now.

## Tier 2 — event-loop latency (synchronous work on the single-threaded wl loop)

These don't burn idle CPU; they cause **input hitches** because the compositor loop is blocked.

### 2.1 Screenshot GPU readback blocks input — `ServerScreenshot.zig:178`, `WmMcpTools.zig:821`
Synchronous per-window texture readback + full-pane render + PNG encode + file write happen on
the event loop. Repeated MCP screenshots of a full-screen browser stall real keyboard/pointer.
**Fix:** move PNG encode + file write off the hot path (defer to an idle-callback, or a worker
thread that only touches the already-copied pixel buffer). Readback itself is unavoidable on
GLES but the encode/write (the slow part) is not. **Risk:** medium. **Verify:** type during a
burst of `teruwm_screenshot` calls, confirm no dropped/late keys.

### 2.2 Bar sysfs EC reads block input — `src/render/BarRenderer.zig:147`
`refreshCachedData` does synchronous ACPI-EC-backed sysfs reads (battery/watts) on the loop,
and the battery + watts TTLs are phase-locked so up to 4 slow EC reads can land in one frame
callback. EC reads can take tens of ms. **Fix:** stagger the TTLs so at most one EC read per
callback, and/or read them from a timer that pre-populates the cache off the paint path.
**Risk:** low. **Verify:** measure frame-callback duration with battery widget enabled.

### 2.3 Bar palette self-sustaining full-refresh-rate repaint — `src/compositor/Bar.zig:240`
While the launcher palette is open, `Bar.render` full-damages every frame → a 60 fps repaint
loop for a static menu. **Fix:** only re-damage the bar when its content signature changes
(the `last_top_sig`/`last_bottom_sig` machinery already exists — see 3.1). **Risk:** low.

## Tier 3 — safe, self-contained wins (low risk, unit-verifiable)

- **3.1 `Bar.create` leaves fields undefined — `src/compositor/Bar.zig:92`.** `allocator.create`
  + field-by-field init skips the declaration defaults, so `last_top_sig`, `last_bottom_sig`,
  `dirty`, `cache_dirty` are `undefined` — the change-detection in 2.3 reads garbage on frame 1.
  **Fix:** initialize the struct with `.{ ... }` (defaults apply) instead of field-by-field, or
  set the four fields explicitly. Trivial; compositor build verifies it.
- **3.2 Wayland surface never sets `set_opaque_region` — `src/platform/linux/wayland.zig:748`.**
  ARGB8888 buffer whose pixels are always fully opaque, but no opaque region declared, so the
  host compositor alpha-blends every frame and can't occlusion-cull teru when covered.
  **Fix:** set the full-surface opaque region once on configure. Pure win, no output change.
  **Verify:** run under a host compositor, confirm no visual change + check occlusion.
- **3.3 Lingering selection disables the throttle — `src/compositor/TerminalPane.zig:472`.** A
  completed (still-visible) selection permanently forces full-rate repaints for that pane.
  **Fix:** only bypass the throttle while a selection *drag* is in progress, not while a static
  selection is shown.
- **3.4 ProcessGraph unbounded growth — `src/graph/ProcessGraph.zig:98`.** The 1024-node cap
  doesn't apply to *running* nodes, so hostile/verbose pane output can grow the graph and its
  duped strings without bound (slow leak + per-query cost). **Fix:** cap running nodes too, or
  evict oldest. **Verify:** unit test feeding >1024 process events.

## "Other things we'd benefit from" (beyond raw perf)

### Remaining confirmed-critical correctness fixes (not yet applied — need your go-ahead)
- **`Server.zig` shutdown UAF (`:1028`, `:1050`):** `deinit` runs *after* `wl_display_destroy`
  (its own comments say so, and deliberately skip timers/clipboard for that reason) yet still
  calls `bar.deinitExecs()` and `wm_mcp.deinit()`, both of which `wl_event_source_remove` on the
  freed loop. **Fix:** move those two into a `releaseTimers`-style defer in `main.zig` that runs
  *before* `wl_display_destroy`, matching the established pattern. Verify: clean SIGTERM shutdown
  under ASan / a debug build, plus the hot-restart path.
- **`WmConfig` by-value dangling slices (`:818`, `:1090`):** bar-format and workspace-startup
  slices point into a struct returned **by value**; only Zig's result-location elision keeps
  them valid today — fragile across compiler bumps (you just did one). **Fix:** have `load`
  fill a caller-provided `*WmConfig`, or re-point the slices into `self` after assignment.

### High-value user-facing bugs the audit surfaced (unverified, worth confirming)
- `Grid.markRowDirty` clobbers the `grid.dirty = true` all-dirty sentinel (`Grid.zig:884`) —
  full-repaint requests from mouse/MCP/pane code get silently narrowed to one row. This is the
  *counterpart* to Tier 1: fix the render path AND this, together.
- `Multiplexer.closePane` reselect order (`:279`) — closing the active pane in a split tree can
  leave no focused pane; keystrokes silently dropped.
- `Scrollback.trimOldest` wipes the entire buffer when only one keyframe exists (`:303`) — the
  steady state for any `scrollback_lines <= 100`.
- `VtParser` DECSET/DECRST honors only `params[0]` (`:1089`) — combined `ESC[?1006;1000h` from
  the system terminfo silently never enables ncurses mouse support.

### Zig 0.17-dev.1417 modernization (low priority, all currently low-severity)
- `src/compositor/Launcher.zig:91` hand-rolled libc `opendir`/`readdir` with a duplicated
  `dirent` layout, justified by a stale "Zig 0.16 compat" comment — `io` is already threaded to
  the call site, so `std.Io.Dir` iteration replaces it.
- `src/server/protocol.zig:90` `Command.fromByte` hardcodes `b <= 21` (silently drops commands
  if the enum grows) — `std.enums.fromInt` does this safely.
- Hand-defined `POLL`/`WNOHANG` constants duplicating std values (`daemon.zig:38`,
  `TuiScreen.zig:330`).
- The stdlib termios typo is fixed upstream, so `tools/zig-lib-fix.sh` is now a no-op — keep it
  (self-healing) or delete once you're sure no other machine runs an older dev build.
