## CRITICAL (11)

### agent/MCP

- **`src/agent/PaneBackend.zig:519`** (bug) **✓CONFIRMED** — sendNdjson ignores write() results: a client that disconnects mid-exchange raises SIGPIPE and kills the entire terminal; EAGAIN/partial writes silently corrupt the NDJSON stream
  - sendNdjson does `_ = std.c.write(self.client_fd, data.ptr, data.len)` then a second unchecked write for the trailing '\n'. (1) SIGPIPE: writing to an AF_UNIX stream socket whose peer has closed delivers SIGPIPE with default disposition = terminate. The teru binary never ignores SIGPIPE — verified by repo-wide grep: the only `signal(SIGPIPE, SIG_IGN)` calls are in vendor/miozu-wlr-glue.c (build.zig compiles that only into the compositor module), and the installed 0.17-dev stdlib start code has no maybeIgnoreSigpipe/keep_sigpipe. So if the Claude Code client exits between our poll() read and the response write (or before a checkExits push at line 511 lands — client_fd staleness is only detected on the next read), one write kills the whole terminal and every shell in it. (2) The fd is O_NONBLOCK (ipc.zig:218): a full socket buffer means EAGAIN drops the response entirely (client hangs forever awaiting its JSON-RPC reply — capture responses approach 64KB) or a partial write / lost trailing newline desyncs framing for every later message. Contrast McpServer.emitEvent (src/agent/McpServer.zig:185-209), which was already fixed to check errno, distinguish EAGAIN, and drop the subscriber on real errors — PaneBackend never got that fix.
  - _Fix:_ M: ignore SIGPIPE once at windowed-mode startup (or use send() with MSG_NOSIGNAL instead of write()); check the write result — on EPIPE/other hard errors close and clear client_fd, on EAGAIN/short write either retry-drain into a small pending-output buffer flushed from poll() or at minimum drop the client so framing can't desync. Mirror the emitEvent errno logic.

### modes

- **`src/modes/windowed.zig:1608`** (bug) **✓CONFIRMED** — Vi cursor overlay `for (cy..max_y)` / `for (cx..max_x)` panics (negative range = integer overflow) whenever the vi cursor lies outside the active pane's rect — trivially reachable in any split layout and after resize/font-zoom while vi mode is active
  - ViMode is entered with the FULL-WINDOW grid dims (windowed.zig:976 `vi_mode.enter(grid_rows, grid_cols, ...)`), but the overlay renderer uses `mux.getActivePaneRect(...)` (Multiplexer.zig:113), which returns the active pane's layout SUB-rect. In a split, the pane is roughly half the window, while ViMode lets the cursor roam 0..global_rows-1 / 0..global_cols-1 (ViMode.zig:166-169 clamps against its own stale `grid_cols`/`grid_rows`; handleKey line 78 refreshes only `total_rows`, never rows/cols — same after a window shrink or `applyFontZoom`). So `G` in a horizontal split, or `$` in a vertical split, yields cy = pr.y + vrow*cell_h > pr.y+pr.height (resp. cx > pr.x+pr.width), making max_y/max_x (the `@min` at 1606-1607) SMALLER than the loop start. I verified on this exact toolchain (0.17.0-dev.1417) that `for (a..b)` with a > b panics "integer overflow" in Debug/ReleaseSafe — and `make release` ships ReleaseSafe, so this is a user-visible crash of the whole terminal. In ReleaseFast the range length wraps and the loop XORs framebuffer pixels outside the pane (visual corruption) until the `py >= cpu.height` / `px >= cpu.width` breaks fire. Note also `Grid.cellAtConst` clamps (Grid.zig:390-394), so the stale dims don't cause OOB reads in word motion — the render overlay is the only crash site I could confirm.
  - _Fix:_ S/M: (1) in windowed.zig:976 pass `pane.grid.rows`/`pane.grid.cols` instead of the global grid dims; (2) in ViMode.handleKey refresh `self.grid_rows = grid.rows; self.grid_cols = grid.cols` from the passed grid (it already receives `*const Grid`) so resize/zoom can't leave stale dims; (3) defensively guard the overlay: `if (cy >= max_y or cx >= max_x) …skip…` before the loops.

### other

- **`src/compat.zig:512`** (bug) **✓CONFIRMED** — forkExecPipeStdin's parent-side pipe write runs with default SIGPIPE disposition — a failed/early-exiting clipboard helper kills the entire teru process on a copy keystroke
  - At compat.zig:512 the original parent does `_ = std.c.write(write_end, data.ptr, data.len)` after both fork children may have already exited. If execve fails in the grandchild (compat.zig:499 → posixExit(1)) — e.g. the hardcoded /usr/bin/wl-copy, /usr/bin/xclip or /usr/bin/pbcopy path doesn't exist (NixOS, non-standard prefix), or xclip exits instantly on 'Can't open display' — every read end of the pipe closes and the write raises SIGPIPE. Verified: nothing in either binary ignores SIGPIPE process-wide (the only `signal(SIGPIPE, SIG_IGN)` calls are inside forked children in vendor/miozu-wlr-glue.c:769/882), and the Zig 0.17.0-dev.1417 stdlib no longer installs the old start-code SIGPIPE-ignore (full grep of /usr/lib/zig/std finds only constants; start.zig has no maybeIgnoreSigpipe). Default SIGPIPE action terminates the process — the whole terminal (all panes, all shells) dies. For payloads under the 64 KiB pipe buffer it is a fork/exec race the parent can lose; for selections larger than the pipe buffer the parent blocks in write() until the reader exits and the kill is deterministic. Callers: src/core/Clipboard.zig:264/268/334 (linuxCopy/macosCopy → Ctrl+Shift+C in windowed/raw teru). teruwm's native copy path uses the wlr seat (ServerClipboard) and is not affected. Secondary defect on the same line: the write result is ignored, so even in the benign case a short write (signal after partial transfer on a >PIPE_BUF payload; WINCH uses SA_RESTART, which does not resume a partially completed write) silently truncates the copied text.
  - _Fix:_ S: ignore SIGPIPE process-wide once at startup in both binaries (sigaction SIG.PIPE → SIG_IGN in main.zig / compositor main — this also protects the daemon's unix-socket writes), and change the parent write into a loop that checks the return value, stopping cleanly on EPIPE and retrying on partial writes.
